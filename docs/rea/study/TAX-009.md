## 3. Gaps and conflicts found

### G-1 (BLOCKER for spec) — Two contradictory replay meanings
- **Model A, faithful replay.** SPEC-TAX-008 purpose ("use original … engine and rounding versions; report unavailable versions"), failure-scenarios #7 and `replay.mmd` (an `EngineRegistry` runs the *matching* version, otherwise `REPLAY_UNAVAILABLE`).
- **Model B, drift check.** SPEC-TAX-004 §5.3 says `replayEngineVersion` is the "Current engine version used in replay". S-RC-014 expects 200 with divergences when the current engine `1.1.0` differs from the original `1.0.0`. SPEC-TAX-003 §6 says the purpose is "to detect algorithmic drift".
- The two models need different code. Model A needs several engine versions kept inside the deployable, with a registry. Model B needs only the current engine, and `REPLAY_UNAVAILABLE` would almost never happen.
- **Candidate resolution (for decision, not decided):** support both modes. The default is Model A, faithful replay: it returns `REPLAY_UNAVAILABLE` when the original engine version is not registered. An explicit `mode=DRIFT_CHECK` mode, or the `engineVersion` override mentioned in OQ-RC-004, runs Model B. MVP could ship only one engine version with the registry interface in place. Owner: architect + domain owner. Linked: OQ-RC-004, OQ-RR-003, LA-009-03.

### G-2 (HIGH) — Rounding version is not persisted
SPEC-TAX-008 says "rounding versions", but neither `tax_calculation` (SPEC-TAX-006/007) nor `CalculationRecord` stores a rounding policy identifier. The rounding policy lives in SPEC-TAX-001 §3 and is not versioned. If OQ-001 changes HALF_EVEN to HALF_UP, a faithful replay cannot be reproduced.
**Options:** (a) make the engine version imply one fixed rounding policy, and document that any rounding change requires a new engine version; or (b) add a `rounding_policy_version` column and field. Option (a) needs no schema change.

### G-3 (HIGH) — Replay must not re-resolve rules
SPEC-TAX-004 §4.3 says replay will "re-execute the full pipeline". Read literally, that calls `TaxRuleGateway` again and may pick a rule published later. ADR-003, failure-scenarios #9 and LA-009-02 all point to rebuilding `TaxRuleSnapshot`s from the stored `rule_snapshot` JSON, with no rule lookup. SPEC-TAX-008 must say this explicitly. SPEC-TAX-004 §4.3 should then be reworded (doc-consistency fix, CLAUDE.md rule 8).

### G-4 (HIGH) — Evidence integrity check is not specified
SPEC-TAX-009 §8 relies on "evidence hash verified on replay" against rule tampering. No spec defines the step, its order or its outcome. Proposed:
1. Recompute `inputCanonicalHash` from `input_snapshot`.
2. Recompute each rule `snapshotHash` and the `evidenceHash` (SPEC-TAX-007 §5.3).
3. Compare with the stored `evidence_hash`, **before** calculating.

On a mismatch, return an explicit integrity failure. Never return a 200 comparison. The code and status are not defined yet; `EVIDENCE_INTEGRITY_VIOLATION` with 409 or 500 is a candidate, to be decided.

### G-5 (MEDIUM) — Error catalog inconsistencies
- `REPLAY_UNAVAILABLE` is named in failure-scenarios but missing from `error-codes.md`, the SPEC-TAX-004 status matrix and OpenAPI. Candidate status is 409 or 422; not decided.
- `error-codes.md` uses `INVALID_REQUEST` and `STORAGE_UNAVAILABLE`. SPEC-TAX-004 uses `VALIDATION_ERROR` and `DEPENDENCY_UNAVAILABLE`. One of the two needs to change.

### G-6 (MEDIUM) — Replay side effects and audit are not defined
- It is not specified whether a replay is persisted, or whether it emits an outbox event (e.g. `TAX_CALCULATION_REPLAYED`).
- RNF-005 (auditability) suggests recording who replayed what and with which verdict.
- If replay writes nothing, it is safe to retry without `Idempotency-Key`. If it writes, its idempotency needs defining.
- **Recommendation for decision:** replay never changes the original records (append-only, INV-OUT-006) and writes at most one audit outbox event per replay.

### G-7 (MEDIUM) — Comparison semantics
The comparison rules are not specified:
- which fields are compared (per component `taxableBase`, `rate`, `amount`, plus `totalTax`, `currency` and component set/order);
- whether `BigDecimal.equals` (scale-sensitive) or `compareTo` is used. Proposal: normalise to the scales in SPEC-TAX-001 §3, then use `equals`;
- the stable `field` path format (`components[i].amount`, `totalTax`);
- how a missing or extra component is reported.

### G-8 (LOW) — Related open questions that block a final spec
- OQ-004 (SPEC-TAX-001): past `operationDate`. Replay reads the stored input, so it does not validate `operationDate <= today` again. Confirm.
- OQ-RR-003: meaning of the snapshot `engineVersion`. This is needed for G-1.
- OQ-OUT-005: only the CBS rule is in `rule_version_id`. Replay must use `rule_snapshot` (both rules), not the FK.

### Already covered (no gap)
- **Tenant isolation:** `loadById(tenantId, id)`, with a cross-tenant request giving the same 404 as a missing one (SPEC-TAX-007 §3, SPEC-TAX-009 §8, INV-RC-004).
- **Authorisation:** the `tax:replay` scope (SPEC-TAX-009 §3.2, S-SEC-012).
- **Decimal wire format:** values sent as strings (SPEC-TAX-004 §8).

## 4. Clean Architecture placement (ADR-008) — proposal

| Element | Layer / module | Notes |
|---|---|---|
| `ReplayCalculationInputBoundary`, `ReplayCalculationOutputBoundary` | `tax-usecases` | Input `(tenantId, calculationId[, mode])`; output is a replay result or a typed error |
| `ReplayCalculationInteractor` | `tax-usecases` | load → verify evidence → rebuild snapshots → choose engine → calculate → compare → (optional) audit |
| `CalculationPersistenceGateway.loadById` | `tax-usecases` port (exists, SPEC-TAX-007) | Reused |
| `EngineRegistry` / `CalculationEngineGateway` (`find(engineVersion): Optional<…>`) | interface in `tax-usecases`; implementations registered in `tax-frameworks` | Only needed for Model A (G-1) |
| `ReplayComparison`, `Divergence` value objects | `tax-domain` | Pure, deterministic; no JSON types |
| Evidence hash recomputation | `tax-domain` (pure function over canonical strings) or `tax-usecases` | SHA-256 via `java.security.MessageDigest` (JDK, not a framework) |
| JSON → `TaxRuleSnapshot` parsing | `tax-interface-adapters` | Keeps JSON out of the domain and use cases |
| Controller, `ReplayResponse` mapping | `tax-interface-adapters` / `tax-frameworks` | Per SPEC-TAX-004 §5.3 |

No Spring, JPA, HTTP or JSON types may appear in `tax-domain` or `tax-usecases`.
